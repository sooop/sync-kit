# 어댑터 가이드

새 앱에 sync-kit 을 붙이는 사람을 위한 가이드다. 앱이 직접 만드는 부분은 어댑터(`SyncAdapter`)와 설정 화면이다. 실행되는 예는 `examples/memory-adapter/`, 화면 상태 로직은 `examples/headless-state/` 에 있다.

## 1. 데이터를 항목으로 나눌 수 있는가

동기화는 항목 단위로 일어난다. 항목은 서버에 따로 저장되고, 버전(rev)이 따로 오르고, 충돌도 따로 판정된다. 데이터가 다음 조건을 만족하면 붙일 수 있다.

| 기준 | 조건 | 어기면 |
|---|---|---|
| 크기 | 항목 하나를 압축·암호화한 base64 가 262,144자(약 256 KB) 이하. 평문이 얼마나 들어가는지는 내용의 압축률에 따라 다르다. md-works 시험에서 평균 13 KB, 최대 38 KB 였다 | 그 항목만 올라가지 않고 `status.oversize` 에 표시된다 |
| 개수 | 공간 하나에 항목 1,000개 이하 | 새 항목이 거부된다(`item_limit`) |
| 총량 | 공간 하나에 5 MB 이하 | `space_full` |
| 독립성 | 한 항목을 고쳐도 다른 항목을 같이 고쳐야 하는 관계가 없다 | 두 기기가 서로 다른 항목을 고치면 합쳐지지만, 관계는 깨질 수 있다 |
| 변경 빈도 | 항목 하나를 하루 수십 번 이상 고치지 않는다. 하루 쓰기 한도는 공간당 300건이다 | `daily_write_limit` |

- 항목 간 참조는 허용하되, 참조 대상이 아직 도착하지 않은 순간을 견뎌야 한다. 어댑터는 이때 `'deferred'` 를 돌려준다(4번).
- 하나의 큰 문서를 쪼개야 한다면 조각 사이의 순서와 참조를 어댑터가 복원할 수 있어야 한다. 복원 규칙이 복잡하면 그 데이터는 동기화에 맞지 않는다.
- 항목을 동시에 두 기기에서 고치면 항목 전체 중 한쪽이 이긴다. 필드를 합치지 않는다. 같은 항목을 여러 기기에서 자주 동시에 고치는 데이터라면 항목을 더 잘게 나눈다.

## 2. 항목 id 설계

항목 id 는 같은 항목을 가리키는 모든 기기에서 같아야 한다. 형식은 `[A-Za-z0-9_-]{1,64}` 이다.

| 방식 | 예 | 쓸 때 |
|---|---|---|
| 앱이 만든 무작위 id | `t-` + 댓글 id | 항목을 만든 기기가 id 를 정하고 그대로 퍼질 때 |
| 이름에서 만든 해시 | `n` + `contentHash(제목.toLowerCase())` | 기기마다 따로 만들어도 같은 이름이면 같은 항목이어야 할 때 |

md-works 는 글에 이름의 해시를 쓴다(`'d' + contentHash(이름.toLowerCase())`, 27자). 글의 로컬 id 가 기기마다 다르기 때문이다. 글감과 스레드는 id 가 무작위라 접두사(`s-`, `t-`)만 붙인다. 접두사를 붙인 길이가 62자를 넘으면 접두사 + `contentHash(id)` 로 줄인다.

주의:

- 이름 해시를 id 로 쓰면 이름 바꾸기는 옛 항목 삭제와 새 항목 생성이다. 이름이 겹치면(대소문자만 다른 경우 포함) 같은 항목이 된다. 앱이 이름 중복을 허용한다면 이름 해시를 쓰지 않는다.
- id 를 만드는 알고리즘을 바꾸면 기존 항목과 끊긴다. 해시를 쓴다면 출력이 바뀌지 않는 함수를 고른다(`contentHash` 는 `core/src/hash.ts` 에 고정돼 있다).
- 서버는 id 를 그대로 본다. 이름 자체를 id 에 넣으면 서버에 이름이 드러난다.

### 로컬 id 를 평문에 넣지 않는다

기기마다 다른 로컬 id 를 평문의 참조 필드에 넣으면, 다른 기기에서는 그 id 가 아무것도 가리키지 않는다. 안정적인 이름이나 키로 바꿔 보내고, 받는 쪽 어댑터가 그 기기의 로컬 id 로 다시 바꾼다.

md-works 의 사례: 스레드는 글을 `docKey`(기기마다 다른 로컬 id)로 가리킨다. 평문에는 `docName`(글 이름)을 넣어 보낸다. `listLocal` 이 `docKey → 글 이름`으로 바꾸고, `apply` 가 `글 이름 → 그 기기의 docKey` 로 바꾼다. 글감의 `attachedDocs`, `orders` 도 같다. 메모리 예제의 댓글(`noteId → 제목`)이 같은 구조다.

## 3. 평문(SyncPlain) 설계와 kind

```ts
interface SyncPlain { v: 1; kind: ItemKind; updatedAt: number; data: unknown /* 앱이 정하는 모양, 삭제 항목은 null */ }
interface LocalItem  { id: string; kind: ItemKind; updatedAt: number; deleted: boolean; data: SyncPlain['data'] }
```

- `kind` 는 `'doc' | 'snippet' | 'thread'` 세 값이다. 어댑터가 `apply` 에서 항목을 종류별로 가르는 데 쓴다. 앱의 항목 종류에 가까운 값을 고른다. `preserveLoser` 와 충돌 시 이력 보존은 `'doc'` 에만 적용된다.
- `data` 는 JSON 으로 직렬화되는 값만 담는다. `undefined` 는 키를 생략하고, 함수·Date·Map 은 쓰지 않는다. 해시는 키를 정렬한 JSON 에서 계산하므로 키 순서는 상관없다.
- `updatedAt` 은 밀리초 시각이고 충돌 판정에 쓴다. 항목을 사용자가 고쳤을 때만 올린다. 앱이 내부 정리(색인 갱신 등)로 올리면 안 된다.
- `updatedAt` 은 변경 감지 해시에 들어가지 않는다. 해시는 `data` 와 삭제 여부로만 계산한다. 시각만 바뀐 항목은 올라가지 않는다.
- 삭제된 항목은 `listLocal` 이 돌려주지 않는다. `apply` 가 받는 삭제 항목은 `deleted: true`, `data: null` 이다.
- `v` 는 평문 형식의 버전이고 값은 1 이다. 앱 데이터의 모양을 바꿀 때는 필드를 추가하는 방식으로 바꾼다. 오래된 앱은 모르는 필드를 읽고 쓰지 못하므로, 모양을 바꾸면 모든 기기를 함께 갱신한다.

## 4. 어댑터 규칙

```ts
interface SyncAdapter {
  listLocal(): Promise<LocalItem[]>;
  apply(item: LocalItem): Promise<'applied' | 'deferred'>;
  preserveLoser(item: LocalItem): Promise<void>;
  removeLocal(item: LocalItem): Promise<void>;
  setApplying?(on: boolean): void;
}
```

### listLocal: 전부 읽거나 던진다

삭제되지 않은 모든 항목을 돌려준다. 읽다가 실패하면 일부를 돌려주지 말고 예외를 던진다. 일부만 돌려주면 엔진은 빠진 항목을 사용자가 지운 것으로 보고 서버에 삭제를 올린다. 서버에 삭제가 올라가면 다른 기기에서도 지워진다. 항목 6개 이상이 한꺼번에 사라지고 그 수가 전체의 절반 이상이면 대량 삭제 가드가 푸시를 멈추지만, 그보다 작은 누락은 막지 못한다.

- 저장소가 아직 열리지 않았거나 로드 중이면 기다리거나 던진다. 빈 목록을 돌려주지 않는다.
- 앱에 저장 대기 중인 편집이 있으면 먼저 저장한 뒤 읽는다(md-works 는 `host.prepare()`).
- 변환할 수 없는 항목은 건너뛰되(md-works 는 글이 없는 스레드를 건너뛴다), 건너뛰는 규칙이 결정적이어야 한다. 같은 상태에서 항상 같은 결과를 내야 한다.

### apply: 쓴 데이터와 다시 읽은 데이터의 해시가 같아야 한다

`apply(item)` 로 쓴 뒤 `listLocal()` 이 그 항목에 대해 돌려주는 `data` 는 `item.data` 와 해시가 같아야 한다. 해시가 다르면 엔진은 방금 받은 항목을 로컬에서 고친 것으로 보고 다시 올린다. 서버 rev 가 오르면 다른 기기가 그것을 받아 적용하고, 같은 일이 되풀이된다(dirty 루프). 쓰기 한도가 이 루프로 소진된다.

어긋나는 흔한 원인:

- 받은 값을 가공해서 저장한다(제목 앞뒤 공백 제거, 줄바꿈 정규화, 대소문자 맞춤).
- 저장소가 값을 바꿔 돌려준다(빈 배열을 `undefined` 로, 숫자를 문자열로, 기본값 채우기).
- 읽을 때 파생 값을 `data` 에 넣는다(현재 시각, 정렬되지 않은 집합).
- 참조 필드의 변환이 왕복하지 않는다(이름 → 로컬 id → 이름으로 돌아온 표기가 원래와 달라진다).

통합 테스트로 확인한다. 항목마다 `apply` 한 뒤 `listLocal` 결과와 `hashItem()`(코어가 내보낸다)을 비교하는 시험이면 충분하다. `examples/memory-adapter/adapter.test.ts` 의 왕복 안정성 시험이 예다.

### 참조를 풀 수 없으면 'deferred'

항목이 가리키는 대상이 로컬에 아직 없으면 쓰지 말고 `'deferred'` 를 돌려준다. 엔진은 같은 동기화에서 받은 변경분을 모두 적용한 뒤 보류 항목을 한 번 더 적용한다. 그때도 못 풀면 보류 상태로 남고, 다음 동기화에서 다시 시도한다. 대상이 영영 오지 않는 항목(삭제된 부모의 자식)은 보류로 남을 수 있다.

- 모르는 종류의 항목은 `'applied'` 를 돌려주고 무시한다. `'deferred'` 로 답하면 계속 재시도한다.
- 삭제 항목(`deleted: true`)은 참조를 풀 필요가 없으므로 항상 `'applied'` 를 돌려준다.

### preserveLoser

충돌에서 진 쪽의 항목이 넘어온다. 본문이 사라지지 않게 앱의 이력 저장소에 남긴다. `kind` 가 `'doc'` 인 항목에만 불린다. 이력이 없는 앱이라면 빈 함수여도 되지만, 그러면 진 본문이 사라진다. 이력에 남기는 것은 로컬 기록일 뿐 서버에 올리지 않는다.

- 대상 항목을 로컬에서 찾을 수 없으면 아무것도 하지 않는다.
- 같은 내용을 두 번 남기지 않게 이력의 id 를 내용에서 만든다(md-works).

### removeLocal: 되돌릴 수 없다

서버에 없는 항목을 사용자가 "이 기기에서 지우기"로 고른 경우에만 불린다. 휴지통으로 옮기지 말고 저장소에서 완전히 지우는 것이 계약이다. 서버에도 없으므로 복구할 곳이 없다. 사용자에게 되돌릴 수 없다고 한 번 확인한 뒤에 부른다(엔진의 `resolveResync('delete')`).

### setApplying

엔진이 `apply`·`removeLocal` 을 부르기 전에 `setApplying(true)`, 끝나면 `setApplying(false)` 를 부른다. 이 사이에 일어나는 쓰기에는 두 가지를 멈춘다.

- 앱의 쓰기 감지(`markDirty` 호출). 원격 반영이 로컬 변경으로 보여 되돌려 올라가는 것을 막는다.
- 앱의 정리 작업(이미지 gc 등). 반영이 끝나기 전에 참조가 비어 보이는 항목을 정리하지 않게 한다.

`setApplying` 호출은 중첩될 수 있으므로 깊이를 센다. 마지막 `false` 에서 화면을 한 번 갱신한다. 구현은 선택이다.

## 5. 한 브라우저에서 엔진은 한 탭에서만

같은 브라우저의 탭 여러 개가 각자 엔진을 돌리면 서로 rev 를 다투며 충돌과 쓰기를 낭비한다. Web Locks 로 한 탭만 엔진을 돌린다.

```ts
if (navigator.locks) {
  void navigator.locks.request('my-app-sync-engine', async () => {
    startEngine();                                   // 락을 쥔 탭만 엔진을 시작한다
    await new Promise<void>(() => { /* 탭이 닫힐 때까지 락을 쥔다 */ });
  });
} else {
  startEngine();
}
```

락을 쥔 탭이 닫히면 기다리던 탭이 락을 받아 이어서 시작한다. 락 이름은 앱마다 고유하게 둔다. `examples/headless-state/controller.ts` 가 이 패턴과 연결 해제 시의 락 해제를 구현한다. 락을 못 얻은 탭의 화면은 엔진 상태를 받지 못하므로, 동기화 대화상자에서 "다른 탭에서 동기화 중"을 보이는 것을 권한다.

## 6. 동기화되지 않는 것

항목에 넣지 않은 데이터는 동기화되지 않는다. 이미지·첨부 파일이 대표적이다. 크기가 항목 한도(256 KB)에 비해 크고 쓰기 한도를 빠르게 소진하기 때문이다.

- 항목 본문의 참조(예: md-works 의 `idb:` 이미지 참조)는 그대로 동기화한다. 참조 대상이 없는 기기는 깨진 이미지 자리에 "이 기기에 없는 이미지" 안내를 보인다.
- 설정 화면에 동기화되지 않는 것을 적는다. md-works 는 "이미지는 동기화되지 않습니다. 다른 기기에서 보려면 백업 번들로 옮기세요"라고 적는다.
- 이력처럼 기기마다 따로 두는 데이터도 화면에 적는다.
- 어댑터는 동기화되지 않는 데이터를 `listLocal` 에 넣지 않는다.

## 7. 설정 항목 체크리스트

| 항목 | 규칙 |
|---|---|
| appId | `^[a-z0-9-]{1,32}$`. 서버의 `ALLOWED_APPS` 와 같은 값. 한 번 정하면 바꾸지 않는다. 바꾸면 같은 동기화 키로도 다른 공간이 된다 |
| Worker 주소 | `https://` 로 시작한다. `localhost`·`127.0.0.1` 만 `http://` 를 허용한다. 입력의 끝 슬래시를 지운다 |
| 동기화 키 | 앱이 `generateSyncKey()` 로 만든다. 사용자가 정하게 하지 않는다. 만든 직후 한 번 보여 주고 따로 보관하라고 안내한다. 잃으면 복구할 수 없다는 점을 적는다 |
| 키 입력 | `normalizeSyncKey()` 가 공백·소문자를 정리한다. `null` 이면 형식 오류로 안내한다 |
| 키 보관 | 설정은 앱의 저장소(예: localStorage)에만 둔다. 번들·내보내기·백업·로그에 넣지 않는다 |
| 초대 코드 | 새 공간을 만드는 첫 요청에만 보낸다. 연결에 성공하면 설정에서 지운다. 다른 기기의 연결에는 필요 없다 |
| 연결 해제 | 이 기기의 키와 설정만 지운다. 항목은 남긴다. 다른 공간에 연결하기 전에 메타 저장소(`clear()`)를 지운다 |
| 상태 표시 | `status.phase`, `lastSyncAt`, `lastError`, `usage`, `oversize`, `resync`, `massDelete` 를 화면에 보인다. 문구는 `core/src/syncLabels.ts` 와 `examples/reference-dialog-svelte/README.md` 를 참고한다 |

## 8. 점검 목록

붙인 뒤 실제 서버(또는 `server/test/d1shim.ts` 의 모의 D1)에서 다음을 확인한다.

| 점검 | 방법 | 기대 결과 |
|---|---|---|
| 오프라인 편집 후 재접속 | 오프라인에서 항목을 고치고 앱을 닫았다 연다. 온라인으로 바꾼다 | 재접속 후 서버에 올라가고 다른 기기에 나타난다 |
| 두 기기 충돌 → 이력 확인 | 두 기기를 오프라인으로 두고 같은 항목을 각각 고친 뒤 차례로 연결한다 | 한 값으로 수렴하고, 진 본문이 충돌을 감지한 기기의 이력에 남는다 |
| 삭제 전파 | 한 기기에서 항목을 지우고 동기화한다 | 다른 기기에서도 지워진다 |
| 왕복 안정성 | 기기 A 에서 항목을 만들고 기기 B 가 받은 뒤, B 에서 동기화를 세 번 더 돌린다 | B 는 아무것도 올리지 않는다. 서버의 rev 가 더 오르지 않는다 |
| 대량 삭제 가드 | 로컬 저장소를 비운 것처럼 `listLocal` 이 빈 목록을 돌려주게 한다(항목 6개 이상) | `status.massDelete` 가 채워지고 푸시가 멈춘다. "서버 사본으로 되돌리기"로 복구된다 |
| 틀린 키 | 다른 키로 연결한다 | 401 로 멈추고(`unauthorized`) 키 다시 입력 안내가 나온다. 서버의 기존 공간에는 영향이 없다 |
| 참조 보류 | 부모보다 자식이 먼저 도착하는 순서를 만든다 | 자식이 `'deferred'` 가 되었다가 같은 동기화에서 적용된다 |
| 한도 | 항목 한도를 넘는 데이터를 만든다 | 그 항목만 `oversize` 로 표시되고 나머지는 올라간다 |
| 탭 두 개 | 같은 앱을 탭 두 개에서 연다 | 한 탭만 요청을 보낸다 |
