# 구조와 동작 원리

sync-kit 은 앱의 데이터를 항목으로 나눠 브라우저에서 암호화하고, Cloudflare Worker 와 D1 에 올려 기기 사이에서 맞춘다. 서버는 암호문만 안다.

## 구성도

```
브라우저(기기 A)                                            Cloudflare 무료 계정
┌──────────────────────────────────────┐                  ┌───────────────────────────┐
│ 앱 저장소                              │                  │ Worker (server/src)        │
│   ▲ listLocal / apply / …            │                  │   POST /v1/sync            │
│ 어댑터 (앱이 구현, SyncAdapter)         │                  │   GET  /v1/health          │
│   ▲                                  │   HTTPS + JSON   │         │                  │
│ 엔진 (core: createSyncEngine)  ────────┼──────────────────▶         ▼                  │
│   ├ 코덱  JSON → deflate → AES-GCM    │  blob = 암호문     │ D1 (server/schema.sql)     │
│   ├ 전송  요청·재시도·헤더               │                  │   spaces  공간별 카운터      │
│   └ 메타 저장소 (IndexedDB)            │                  │   items   항목별 rev·blob   │
└──────────────────────────────────────┘                  └───────────────────────────┘
        기기 B, C … 는 같은 동기화 키로 같은 공간에 연결한다
```

| 부분 | 위치 | 하는 일 |
|---|---|---|
| 서버 | `server/` | 인증, 한도 검사, rev 비교, 변경 목록 제공. 평문을 알지 못한다 |
| 코어 | `core/src/` | 키 파생, 암호화, 전송, 변경 감지, 충돌 판정, 스케줄 |
| 어댑터 | 앱이 구현 | 앱 저장소와 항목 사이를 변환한다. 계약은 `core/src/protocol.ts` 의 `SyncAdapter` |
| 메타 저장소 | 코어가 제공 | 항목별 마지막 rev·해시와 커서를 기기에 둔다. `createIdbMetaStore()`(IndexedDB `works-sync`), 테스트용 `createMemoryMetaStore()` |

## 공간과 항목

공간은 동기화 키 하나에 대응하는 서버 쪽 데이터 묶음이다. 같은 앱 식별자(appId)와 같은 동기화 키를 쓰는 기기는 같은 공간을 본다. 서버가 아는 공간 식별자는 키에서 파생한 해시뿐이다.

항목은 동기화의 최소 단위다. 서버는 항목마다 다음을 둔다.

| 필드 | 뜻 |
|---|---|
| `item_id` | 앱이 정한 항목 id. `[A-Za-z0-9_-]{1,64}` |
| `rev` | 서버가 매기는 버전. 항목을 쓸 때마다 1 오른다. 처음 만들 때 1 |
| `seq` | 공간 전체의 변경 순번. 쓸 때마다 공간의 `seq` 가 오르고 그 값이 항목에 붙는다 |
| `deleted` | 삭제 표시. 삭제 항목의 `blob` 은 빈 문자열이다 |
| `blob` | 암호화된 평문(base64) |

기기는 마지막으로 받은 `seq` 를 커서로 기억하고, 다음 요청에서 그 커서보다 큰 `seq` 의 항목을 받는다.

## 키 파생

동기화 키는 앱이 만드는 128비트 무작위 값이다. Crockford base32 26자이고, 화면에는 4자씩 `-` 로 끊어 보인다(`generateSyncKey()`). 입력은 `normalizeSyncKey()` 로 공백·하이픈을 지우고 대문자로 바꾸며 `I`·`L` 을 `1`, `O` 를 `0` 으로 읽는다.

정규형 키(하이픈 없는 26자)와 appId 에서 세 값을 파생한다(`deriveKeys(syncKey, appId)`).

| 값 | 계산 | 쓰임 |
|---|---|---|
| 공간 식별자 | hex(SHA-256(`space:` + appId + `:` + 키)) | `X-Space-Id` 헤더 |
| 인증 토큰 | hex(SHA-256(`auth:` + appId + `:` + 키)) | `Authorization: Bearer` 헤더 |
| 암호화 키 | HKDF-SHA-256(입력 = 키의 UTF-8, salt = `sync-v1`, info = `enc:` + appId) → AES-GCM 256비트, 추출 불가 | 항목 암호화 |

서버는 인증 토큰의 SHA-256 만 저장한다. 암호화 키는 기기를 떠나지 않는다. appId 가 파생에 들어가므로 appId 를 바꾸면 같은 키로도 다른 공간·다른 암호화 키가 된다.

## 암호화 형식

```
blob = base64( IV(12바이트) ‖ AES-GCM 암호문 ‖ 태그(16바이트) )
암호문 = AES-GCM( deflate( UTF-8( JSON.stringify(SyncPlain) ) ),  IV = 무작위 12바이트,  AAD = UTF-8(항목 id) )
```

- 압축은 `fflate` 의 `deflateSync`(수준 6, 원시 deflate)다.
- 항목 id 를 AAD 로 묶으므로 다른 항목의 blob 을 옮겨 붙이면 복호화에 실패한다.
- 복호화 실패(키 불일치·변조·id 불일치)는 `SyncCryptoError` 로 올라오고, 엔진은 `crypto` 문제로 멈춘다.
- `MAX_ITEM_BYTES` 는 base64 문자열의 길이에 적용한다.

## 평문 형식

암호화 전의 평문은 `SyncPlain` 이다.

```ts
interface SyncPlain {
  v: 1;
  kind: 'doc' | 'snippet' | 'thread';
  updatedAt: number;          // 밀리초. 충돌 판정에 쓴다
  data: unknown;   // 앱이 정하는 모양. 삭제 항목은 null
}
```

`kind` 의 세 값과 `data` 의 모양은 md-works 가 정한 것이다(글·글감·스레드). 다른 앱은 의미가 맞는 값을 골라 쓴다(예: 본문이 있는 항목은 `doc`). 항목 id 와 `data` 안의 필드를 정하는 방법은 [ADAPTER-GUIDE.md](ADAPTER-GUIDE.md) 에 있다.

## 동기화 한 번의 흐름

엔진은 풀 → 푸시 → 풀 순서로 한 번을 돈다(`syncNow()`).

1. 풀: 커서를 보내 변경분을 받는다. `hasMore` 가 참이면 반복한다. 받은 항목을 복호화하고, 로컬과 같으면 메타만 갱신하고, 로컬이 바뀌지 않았으면 `adapter.apply` 로 반영하고, 로컬도 바뀌었으면 충돌 판정을 한다.
2. 보류 항목 재시도: `apply` 가 `'deferred'` 를 돌려준 항목을 풀이 끝난 뒤 한 번 더 적용한다.
3. 푸시: `adapter.listLocal()` 의 각 항목 해시를 메타의 해시와 비교해 바뀐 항목을 올린다. 메타에 있는데 로컬에 없는 항목은 삭제로 올린다. 올리기 전에 대량 삭제 가드를 검사한다. 요청은 항목 20개, 본문 약 400 KB 단위로 나눈다.
4. 서버 응답의 `accepted` 는 메타의 rev 를 갱신하고, `conflicts` 는 충돌 판정으로 보낸다. 로컬이 이긴 항목은 서버의 rev 를 `baseRev` 로 다시 올리며, 이 재시도는 최대 3회다.
5. 푸시한 것이 있으면 풀을 한 번 더 한다.

변경 감지 해시는 `{삭제 여부, data}` 를 키 정렬 JSON 으로 만든 문자열의 `contentHash` 다. `updatedAt` 은 해시에 들어가지 않는다. 그래서 `listLocal` 이 돌려주는 `data` 가 같으면 변경이 없는 것으로 본다.

### 스케줄

| 동작 | 값 |
|---|---|
| 시작 | `start()` 가 즉시 한 번 동기화한다 |
| 폴링 | 화면이 보일 때 3분마다 |
| 편집 후 푸시 | `markDirty()` 뒤 5초 디바운스 |
| 같은 항목의 푸시 간격 | 30초에 한 번. 오늘 쓰기가 한도의 80% 이상이면 5분 |
| 화면이 숨겨질 때 | 대기 중인 디바운스를 바로 실행한다 |
| 다시 온라인 | `online` 이벤트에서 실행한다 |
| 서버 5xx | 30초(또는 `Retry-After`)에서 시작해 2배씩, 최대 10분까지 늘려 재시도한다 |
| 429 | 다음 00:00 UTC 까지 푸시를 멈춘다 |
| 401·403 | 멈춘다. 키나 설정을 바꾼 뒤 `resume()` 한다 |

## 충돌 모델

충돌 단위는 항목 전체다. 항목 안의 필드를 합치지 않는다.

서버는 `baseRev` 가 서버의 `rev` 와 같을 때만 쓴다. 다르면 쓰지 않고 `conflicts` 에 서버의 현재 사본을 돌려준다. 풀에서 받은 항목도 로컬이 바뀐 상태면 충돌로 다룬다. 판정은 이렇다.

- 두 사본의 `updatedAt` 을 비교해 큰 쪽이 이긴다. 같으면 서버 사본이 이긴다.
- 서버 사본이 이기면 서버 사본을 `apply` 하고, 로컬이 이기면 서버의 rev 를 받아 다시 올린다.
- 항목이 `doc` 이면 진 쪽의 본문을 `adapter.preserveLoser` 로 이력에 남긴다. 서버에는 올리지 않는다.

진 본문은 충돌을 감지한 기기의 이력에 남는다. 서버 사본이 이기면 그 기기의 로컬 사본이, 로컬이 이기면 서버 사본이 `preserveLoser` 로 넘어간다. 이력을 어떻게 저장하는지는 어댑터가 정한다. 같은 충돌을 늦게 풀로 받는 기기는 이미 올라간 사본을 그대로 받기만 하고 이력을 남기지 않는다.

삭제와 편집이 충돌하면 `updatedAt` 으로 가린다. 서버의 삭제 사본은 `updatedAt` 을 알 수 없어 0 으로 취급하므로, 다른 기기에서 지운 항목을 로컬에서 고쳤다면 로컬 편집이 이겨 항목이 되살아난다. 반대로 로컬에서 지운 항목을 다른 기기가 고쳤다면 보통 그 편집이 이긴다.

한계:

- `updatedAt` 은 기기의 시계다. 시계가 앞선 기기가 이긴다. 시계가 크게 어긋난 기기가 있으면 최근에 고친 쪽이 질 수 있다. 진 본문은 이력에 남지만 자동으로 되살리지는 않는다.
- 충돌 창: 한 기기의 편집이 다른 기기에 보이기까지 편집 후 5초 디바운스, 같은 항목 30초 간격, 폴링 최대 3분이 겹칠 수 있다. 이 시간 안에 두 기기가 같은 항목을 고치면 충돌이 생긴다.

## 삭제와 보관 기간

삭제는 삭제 표시(`deleted`)로 전파한다. 서버는 삭제 항목의 행을 남기되 `blob` 을 비운다. 보관 기간(`TOMBSTONE_DAYS`, 기본 30일)이 지난 삭제 항목은 서버가 정리한다.

- 정리는 쓰기 요청의 약 5% 에서 실행한다. 보관 기간보다 오래된 삭제 항목을 지우고, 지운 항목 중 가장 큰 `seq` 를 `purged_seq` 에 기록한다.
- 기기의 커서가 0 보다 크고 `purged_seq` 보다 작으면 이 기기는 정리된 삭제를 놓쳤을 수 있다. 서버는 응답에 `resyncRequired: true` 를 넣고, 커서를 0 으로 보고 전체 변경분을 돌려주며, 이 요청의 `push` 는 무시한다.
- 엔진은 서버가 돌려준 항목 목록과 메타를 비교해, 서버에 없는데 로컬에 있는 항목(고아)을 찾는다. 고아가 있으면 `status.resync` 를 채우고 사용자의 선택을 기다린다.

| 선택 | 호출 | 결과 |
|---|---|---|
| 서버에 올리기 | `resolveResync('upload')` | 고아를 새 항목(`baseRev` 0)으로 올린다 |
| 이 기기에서 지우기 | `resolveResync('delete')` | `adapter.removeLocal` 로 지운다. 되돌릴 수 없다 |

고아가 없으면 묻지 않고 커서만 갱신한다. 선택을 기다리는 동안 커서를 저장하지 않으므로, 앱을 닫았다 열면 같은 판정이 반복된다.

대량 삭제 가드는 별개다. 로컬 목록에서 서버에 올라간 항목이 6개 이상 한꺼번에 사라지고 그 수가 전체의 절반 이상이면, 엔진은 푸시를 멈추고 `status.massDelete` 를 채운다. 저장소를 못 읽어 서버가 비워지는 사고를 막는다.

| 선택 | 호출 | 결과 |
|---|---|---|
| 삭제를 서버에도 반영 | `resolveMassDelete('proceed')` | 삭제를 서버에 올린다. 다른 기기에서도 지워진다 |
| 서버 사본으로 되돌리기 | `resolveMassDelete('restore')` | 사라진 항목의 메타를 지우고 커서를 0 으로 돌려 서버에서 다시 받는다 |

## 한도

| 이름 | 기본값 | 의미 | 적용 위치 |
|---|---|---|---|
| `MAX_ITEM_BYTES` | 262,144 | 항목 하나의 blob 길이 | 서버(422 `item_too_large`), 클라이언트(올리지 않고 `oversize` 로 표시) |
| `MAX_SPACE_BYTES` | 5,242,880 | 공간 하나의 blob 합계 | 서버(422 `space_full`) |
| `MAX_ITEMS_PER_SPACE` | 1,000 | 공간 하나의 삭제되지 않은 항목 수 | 서버(422 `item_limit`) |
| `MAX_SPACES` | 60 | 서버 전체의 공간 수 | 서버(403 `forbidden`) |
| `MAX_DAILY_WRITES` | 300 | 공간 하나의 하루(UTC) 쓰기 항목 수 | 서버(429 `daily_write_limit`) |
| `TOMBSTONE_DAYS` | 30 | 삭제 항목 보관 일수 | 서버 |
| `MAX_BODY_BYTES` | 524,288 | 요청 본문 | 서버(413 `body_too_large`) |
| `SOFT_BODY_BYTES` | 400,000 | 클라이언트가 요청을 나누는 기준 | 클라이언트 |
| `MAX_PUSH_ITEMS` | 20 | 요청 하나의 `push` 항목 수 | 서버(413), 클라이언트 |
| `PULL_MAX_ITEMS` | 50 | 응답 하나의 `changes` 항목 수 | 서버 |
| `PULL_MAX_BYTES` | 262,144 | 응답 하나의 `changes` blob 합계(첫 항목은 예외) | 서버 |

앞의 여섯 값은 서버의 `wrangler.toml` 에서 바꾼다. 클라이언트의 `LIMITS` 상수는 기본값이므로, 서버 값을 바꿔도 화면의 사용량 비율과 푸시 간격 조절(쓰기 한도의 80%)은 기본값 기준으로 계산한다. 조정 방법은 [OPERATIONS.md](OPERATIONS.md) 에 있다.

## 보안 모델

- 서버는 암호문만 안다. 항목의 내용과 이름은 기기에서 암호화한 뒤 올린다. 서버가 아는 것은 항목 id, rev, 크기, 시각, 삭제 여부, 항목 수와 변경 패턴이다. 항목 id 를 이름의 해시로 만들어도 짧은 이름은 추측해 맞춰 볼 수 있다.
- 동기화 키가 곧 접근 권한이다. 키를 아는 사람은 공간을 읽고 쓰고 지울 수 있다. 키를 잃으면 복구할 수 없다.
- 초대 코드는 공간 생성만 막는다. 이미 만든 공간의 접근은 막지 않는다. 초대 코드를 아는 사람은 허용된 앱의 새 공간을 만들 수 있고, 공간 수 한도(`MAX_SPACES`)까지 차지할 수 있다.
- 서버는 키와 토큰을 로그에 남기지 않는다.
- 이 암호 설계는 외부 검증을 거치지 않았다.
